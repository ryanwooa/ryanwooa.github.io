From a Frontend Database Architecture to Gradual SSR Migration

Our Original Architecture#

Early on, the project used a frontend database + backend sync model.

When a user opened the site, data was synced from the backend into a local browser database (IndexedDB / Dexie). After that, almost every read on the page went through this local layer instead of hitting the API on each navigation.

The upside was clear: the first load was slow, but everything after that felt very fast. Lists, detail views, filters, and sorting were essentially local reads with almost no network latency—closer to an offline-first web app than a classic SPA.

The downside was just as clear: it was bad for SEO.

Crawlers and social preview bots do not wait for your local sync to finish. They see the initial HTML and JS, not what lives in IndexedDB. Detail page titles, descriptions, and body content showed up empty—or as a generic shell—in search results and Facebook link previews. URLs were often query-based or routed through a single “details” path, which made independent, indexable, shareable pages hard to build.

The product worked. Discoverability did not. That gap is why we eventually moved toward SSR.

Why We Did Not Rewrite Everything at Once#

The frontend-database architecture already powered a large share of pages and components. A full, all-at-once SSR rewrite would have been high risk: huge scope, hard regression testing, and a real chance that TTFB would get worse everywhere.

What we actually did was incremental migration:

  • Start with pages: entry points that get shared and searched—detail pages, home, profile, about/legal—became Server Components that fetch primary data on the server
  • Leave components alone for now: many child components still fetch secondary data with useEffect, close to the old pattern, keeping the change surface manageable
  • Evolve the data layer in parallel: SSR requires the server to query the DB or call APIs directly; the local database slowly stepped back from “single source of truth” to optional or removed

This was not “SSR good, CSR bad.” It was about moving what must be visible to the outside world onto server-rendered HTML without breaking the product.

How We Split Responsibilities During Migration#

Pages: SSR for what must appear in the first screen#

Core detail objects, initial home content, the main profile document, 404 handling, and permission checks—all of these need to exist in the HTML. Without that, SEO, link previews, and correct HTTP semantics (404 vs 200) do not hold up.

We also used this moment to fix URLs: semantic paths, ID + slug, redirects from legacy routes—done together with SSR so we would not accumulate redirect debt later.

Components: keep useEffect, but be deliberate about what they fetch#

Child components did not all need to move to SSR. Comments, favorites, notification state, sidebar extras—many were never on the critical first-screen path. Client-side fetching there still made sense.

The catch: SSR on the page does not mean components can fetch freely. Reads from the local DB were nearly free; every useEffect after migration is a real network call. We had to be intentional—merge requests where possible, cache where it helps (e.g. SWR)—so we would not end up with “SSR made the page faster, but a waterfall of API calls made the experience slower.”

Performance: SSR is not a free lunch#

The old model was slow once, then fast forever. SSR means every request can hit the server again. TTFB and database load need a fresh look.

In practice we traded on a few axes:

  • Primary data on the server, secondary data on the client—not one giant SSR payload
  • Parallelize queries where it helps, but cap concurrency so connection pools do not get exhausted
  • Do not block first HTML on non-critical data—ship the page, let components fill in
  • Public pages like home can use revalidation to reduce cost per hit
  • Guards and redirects on the server—less “flash the wrong page, then redirect” on the client

The question shifted from “how do we make local reads faster?” to “what does the server render, what does the client add, and what does each path cost?”

Decoupling From the Frontend Database Was Part of the Same Effort#

Once pages SSR, Server Components cannot read IndexedDB. The old flow—open site → sync to local → pages read local—no longer works for public and SEO-sensitive routes.

In parallel we moved reads and writes toward backend APIs and shrank the local DB’s role. If you only change rendering and not data entry points, you fight the Server/Client boundary constantly—the server fetches one way, the client still reads locally, and inconsistencies follow.

Rough order: SSR public pages → move their read paths to APIs → leave editor/admin flows for later. You do not need full API coverage before the first SSR page, but both tracks should be planned together.

Lessons Learned (With the Old Architecture in Mind)#

Assuming SSR fixes all slowness—before, pain was first sync; after, pain is server queries and API waterfalls. The bottleneck moves; you have to measure again.

Page is SSR, components still fire many APIs—reads that were invisible with a local DB become N HTTP requests. First paint can feel worse unless you batch, cache, and lazy-load.

Mixing SEO pages and editor flows on one data path—public pages need a server-trustworthy source; editor pages can stay client-heavy, but the boundary must be explicit.

Handling slug, permissions, and 404 on the client—with a local DB, “no data yet” often meant an empty UI; for SEO routes, the server should own notFound, redirects, and canonical URLs.

First load vs every load—the old stack traded cold start for hot-path speed; SSR improves visibility but may add network round trips on each visit. The product has to accept that trade-off. You cannot expect “SEO-grade pages that feel exactly like a local database on every click.”

Relationship to SEO Work#

SSR is a prerequisite for SEO, not a substitute. Sitemaps, robots, metadata, and JSON-LD can come later—but if content still depends on the client and local storage, those tools only help so much.

Our sequence was: make searchable, shareable pages render content and meta on the server first, then add sitemap rules, indexing policy, and Search Console. Otherwise you end up tuning SEO on empty shells.

If Your Stack Looks Similar, Suggested Priorities#

  1. Decide which pages must SSR—details, home, public profiles; not the whole site
  2. Change URLs together with SSR—one pass beats years of redirects
  3. SSR pages + useEffect components can coexist—reasonable, but cap component request volume
  4. Plan API migration alongside page migration—API-ization supports SSR; treat it as coupled work
  5. Set a performance budget separately—TTFB, API count, DB concurrency; do not judge the new stack with the old local-DB expectations

Closing Thoughts#

Our migration was not from “pure CSR” to “pure SSR.” It was from a frontend-database-driven in-app experience to a hybrid model: public pages visible on the server, interactive pages still supplemented on the client.

The old approach traded first sync for later speed—a good deal inside the product, a bad deal for SEO. The new approach trades server-rendered first screens for discoverability, at the cost of redesigning data paths and request strategy.

If you started with local DB + sync, that is not a mistake. It still works well for tool-like, logged-in products. But pages that need to be found and shared eventually have to serve real content from the server. Replacing pages incrementally, leaving components on useEffect for now, and optimizing APIs and requests in parallel is a steady path forward.
