Jest is great for functions and APIs, but it cannot verify full user flows like “click a button → navigate → map loads → modal appears.” In our Next.js project, we built a Playwright E2E setup with three desktop browsers + two mobile viewports, organized by Desktop / Mobile directories. This post is a retrospective, not a rewrite of the official docs.

Why Playwright#

Compared with tools like Cypress, Playwright fit our needs especially well:

  • Native multi-browser support: one API for Chromium, Firefox, and WebKit
  • Mobile emulation: built-in device presets like Pixel 5 and iPhone 12
  • Auth state reuse: log in once with storageState, reuse everywhere
  • Works well with Next.js: webServer can start the dev server automatically; you can also run npm run dev first to speed things up

Jest still handles unit and integration tests; Playwright covers frontend user flows.

Project Structure#

The core idea: layer by layout, split by page, extract shared logic into helpers.

tests/e2e/
├── auth.setup.js              # Log in once, save cookies
├── authentication.spec.js     # Login flow itself (separate project)
├── helpers/
│   ├── pageHelpers.js         # Shared: skip tour, suppress banners, wait for home
│   ├── mapHelpers.js          # Desktop map interactions
│   └── detailHelpers.js
├── desktop/
│   ├── homePage.spec.js
│   ├── detailsPage.spec.js
│   └── searchPage.js
└── mobile/
    ├── homePage.spec.js
    ├── mobileTabBar.spec.js
    └── objsPage2/
        └── objsPage2.map.spec.js

Naming rule: **/*.spec.js. Desktop and Mobile run separately—avoid if (isMobile) branches inside one file.

Configuration: Projects for Multi-Browser + Layering#

playwright.config.ts is the backbone of the whole setup:

import { defineConfig, devices } from "@playwright/test";
import dotenv from "dotenv";
dotenv.config();

export default defineConfig({
  testDir: "./tests",
  timeout: 90 * 1000,
  expect: { timeout: 45 * 1000 },
  fullyParallel: false,
  retries: process.env.CI ? 2 : 0,
  workers: 2,
  reporter: "html",

  use: {
    baseURL: "http://localhost:3000",
    actionTimeout: 15 * 1000,
    navigationTimeout: 30 * 1000,
    trace: "on-first-retry",
  },

  projects: [
    // 1. Run setup first to generate auth state
    {
      name: "setup",
      testMatch: /auth\.setup\.js/,
    },

    // 2. Test login flow separately (no storageState)
    {
      name: "authentication",
      testMatch: /authentication\.spec\.js/,
      use: { ...devices["Desktop Chrome"] },
    },

    // 3. Desktop × three browsers
    {
      name: "chromium",
      testMatch: /desktop\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["Desktop Chrome"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },
    {
      name: "firefox",
      testMatch: /desktop\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["Desktop Firefox"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },
    {
      name: "webkit",
      testMatch: /desktop\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["Desktop Safari"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },

    // 4. Mobile × two devices
    {
      name: "Mobile Chrome",
      testMatch: /mobile\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["Pixel 5"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },
    {
      name: "Mobile Safari",
      testMatch: /mobile\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["iPhone 12"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },
  ],

  webServer: {
    command: "npm run dev",
    url: "http://localhost:3000",
    reuseExistingServer: !process.env.CI,
    timeout: 180 * 1000,
  },
});

Key design decisions:

DecisionReason
testMatch by desktop/mobile pathNo viewport checks in every test
dependencies: ["setup"]Ensures login runs before business tests
fullyParallel: falseAvoids parallel conflicts for write-heavy or shared-data tests
reuseExistingServer: true (local)Skips startup wait when dev server is already running
Global timeout 90sGoogle Maps and Auth0 redirects are slow

Auth0 Login: setup + storageState#

Running through Auth0 on every test is too slow. Use a setup project to log in once and save cookies:

// tests/e2e/auth.setup.js
const { test: setup, expect } = require("@playwright/test");

const authFile = "playwright/.auth/user.json";

setup("authenticate", async ({ page }) => {
  await page.goto("/");
  await page.getByText("Sign In").click();

  await page.waitForURL(/.*auth0.com/);
  await page.locator('input[name="username"]').fill(process.env.AUTH0_USERNAME);
  await page.locator('input[name="password"]').fill(process.env.AUTH0_PASSWORD);
  await page.getByRole("button", { name: "Continue" }).click();

  await page.waitForURL(/localhost:3000/);
  await page.context().storageState({ path: authFile });
});

Put test credentials in .env:

AUTH0_USERNAME=test@example.com
AUTH0_PASSWORD=your_test_password

For anonymous tests, explicitly clear auth state:

test.describe("Unlogged", () => {
  test.use({
    storageState: { cookies: [], origins: [] },
  });
  // ...
});

Keep the login flow itself in authentication.spec.js, under its own project, separate from business tests.

Desktop / Mobile: What to Test and How to Split#

Rule: test shared components once; split forked UI#

Mobile and Desktop often share low-level components (e.g. Card), but the interaction shell differs:

  • Desktop map: marker click → overlay
  • Mobile map: marker click → bottom SlideUpPanel

Buttons triggered by hover on Desktop must be directly visible and tappable on Mobile—do not rely on .hover().

Mobile-specific locators#

Mobile often has duplicate DOM nodes where only one is visible. Plain getByTestId may match a hidden node:

const mobileHomeTab = (page, id) =>
  page.locator(`#${id}`).filter({ visible: true }).first();

const visibleSharePanel = (page) =>
  page.locator("#share-your-experience").locator("visible=true").first();

Helper Layer: Centralize Stability Logic#

Test files should read like user stories. Waiting, retries, and dialog suppression belong in helpers.

Shared helper (pageHelpers.js)#

async function suppressBannerDialogs(page) {
  await page.addInitScript(() => {
    localStorage.setItem("locationPermission", "denied");
    localStorage.setItem("myapp_cookie_consent", "declined");
  });
}

Notes:

  • Use addInitScript to write localStorage before the page loads—more reliable than closing banners after load
  • Use isVisible() instead of hard waits so missing tours do not cause timeouts

Cross-browser navigation retry (mapHelpers.js)#

Firefox and WebKit often throw NS_BINDING_ABORTED during client-side routing races; Chromium usually does not:

export async function gotoStable(page, url, retries = 3) {
  for (let attempt = 0; ; attempt++) {
    try {
      await page.goto(url);
      return;
    } catch (err) {
      const isAbort =
        /NS_BINDING_ABORTED|interrupted by another navigation|frame was detached/i.test(
          err?.message ?? ""
        );
      if (!isAbort || attempt >= retries) throw err;
      await page.waitForLoadState("load").catch(() => {});
    }
  }
}

Issues that only appear in one browser are worth encoding in helpers with comments—future you will thank you.

How to Write Test Files#

1. Split anonymous vs logged-in with describe#

test.describe("Unlogged", () => {
  test.use({ storageState: { cookies: [], origins: [] } });
  // Public pages, cookie banner, footer
});

test.describe("Logged In", () => {
  test.beforeEach(async ({ page }) => {
    await page.goto("/");
    await skipTourIfVisible(page);
  });
  // Features that require login
});

2. Use serial mode for dependent flows#

Create → edit → delete chains:

test.describe("Logged In Map View", () => {
  test.describe.configure({ mode: "serial", timeout: 90000 });
  // Firefox login + Google Maps init can exceed 60s
});

3. Prefer role / testid over fragile CSS#

// Good
await page.getByRole("button", { name: "Delete" }).click();
await page.getByTestId("footer").toBeVisible();

// Third-party map components may require class selectors
await page.locator(".gm-style").toBeVisible();

Add data-testid on critical interactions during development—E2E gets much more stable.

4. Skip when data is missing, do not hard-fail#

test.skip((await link.count()) === 0, `Top Contents don't have ${type}`);

When test data is unstable, skip beats a wall of red.

Multi-Browser Lessons Learned#

In practice, the three browsers diverged more than expected:

IssueSymptomFix
Firefox slownessMaps init + login setup exceeds 60sLocal timeout: 90000
WebKit navigation racepage.goto aborted by client routinggotoStable retry
Google Maps markersClick timing varies by enginedispatchEvent("click") + retry loop
Hidden DOM nodesMobile duplicate markup, multiple getByText matches.filter({ visible: true })
Third-party iframeMaps lives inside iframeStable outer anchors like .gm-style

Bottom line: passing in Chromium does not mean passing everywhere. In CI, run at least Firefox or WebKit alongside Chromium.

How to Run#

# Full suite (start dev server manually first for speed)
npm run test:e2e

# UI mode for debugging
npm run test:e2e:ui

# Desktop Chromium only
npx playwright test --project=chromium

# Mobile only
npx playwright test --project="Mobile Chrome"

# Single file
npx playwright test tests/e2e/desktop/homePage.spec.js

# View report
npm run test:e2e:report

Local tip: start the dev server first, then run tests. With reuseExistingServer: true, Playwright reuses the running server and avoids waiting for webServer startup.

Closing Thoughts#

Playwright’s value is not just “automating clicks”—it is keeping test cost under control through project structure:

  • Projects manage the browser and device matrix
  • Directory layering handles Desktop / Mobile differences
  • setup + storageState handles Auth0 login
  • helpers handle stability and cross-browser patches

Going from a few scattered specs to 30+ files covering home, map, details, editing, and search was not about writing more assertions—it was about getting layering and reuse right first. If you are on Next.js with third-party auth and a responsive dual-layout UI, this structure is ready to copy.
