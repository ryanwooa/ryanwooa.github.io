When you ship a web app, getting features working is only half the job. The other half is making sure search engines can find your site and understand each page correctly. This post walks through SEO for the Next.js App Router, based on a real project refactor: what SEO is, why it matters, what to configure, and how to manage it after launch.

What Is SEO?#

SEO (Search Engine Optimization) is a set of technical and content practices aimed at helping your site appear in organic search results on Google, Bing, and similar engines.

Search engines roughly follow three steps:

  1. Crawl – bots visit your URLs
  2. Index – they analyze page content and store it
  3. Rank – they return relevant results when users search

SEO is not about tricking algorithms. It is about helping crawlers understand your pages: title, description, canonical URL, and which pages should not be indexed.

For Next.js projects, SEO mostly lives in:

  • Meta tags in the HTML <head>
  • Structured data (JSON-LD)
  • robots.txt and sitemap.xml
  • URL structure, canonical URLs, and redirects
  • Blocking non-production environments from indexing

Why Bother With SEO?#

1. Organic traffic compounds over time#

Paid ads stop when you stop paying. Properly indexed pages can keep bringing visitors with very low marginal cost.

2. Dynamic content sites need it most#

User-generated routes, posts, events, and profile pages are all potential entry points. Without generateMetadata, a sitemap, and structured data, crawlers often only see the same empty HTML shell.

3. Social sharing uses the same meta tags#

WeChat, Twitter, Facebook, and Pinterest read Open Graph and Twitter Card tags when building link previews. SEO and share previews usually share one configuration.

4. Avoid “we launched but Google can’t find us”#

Common causes:

  • Staging environments getting indexed
  • Login walls blocking crawlers
  • No sitemap
  • Duplicate URLs without a canonical

All of these can be handled systematically in Next.js.

What to Configure in the Next.js App Router#

Below is a layered breakdown. Code uses generic examples you can drop into your own project.

1. Environment split: block indexing outside production#

If test or staging sites get indexed, they compete with production and may expose unreleased content.

Control this in the root layout via environment variables:

// app/layout.js
const isProd = process.env.NEXT_PUBLIC_BASE_URL === "https://www.example.com";

export const metadata = {
  title: {
    default: "My App",
    template: "%s - My App",
  },
  description: "Application description",
  openGraph: {
    type: "website",
    siteName: "My App",
    title: "My App",
    description: "Application description",
    images: [{ url: "/images/og-default.jpg", width: 1200, height: 630 }],
  },
  // Non-production: site-wide noindex
  ...(!isProd && { robots: { index: false, follow: false } }),
};

robots.js can add a second layer: non-production returns disallow: /:

// app/robots.js
const BASE_URL = process.env.NEXT_PUBLIC_BASE_URL;
const isProd = BASE_URL === "https://www.example.com";

export default function robots() {
  if (!isProd) {
    return {
      rules: [{ userAgent: "*", disallow: "/" }],
    };
  }

  return {
    rules: [
      {
        userAgent: "*",
        allow: "/",
        disallow: [
          "/settings/",
          "/admin/",
          "/api/",
          // Edit pages, messages, etc. that require login
        ],
      },
    ],
    sitemap: `${BASE_URL}/sitemap.xml`,
  };
}

Key idea: allow public pages, disallow private ones. That is cleaner than opening everything and relying on per-page noindex alone.

2. Global metadata + per-page generateMetadata#

The App Router Metadata API is the recommended approach instead of manually editing <head>.

Root layout: site name, default title template, default OG image.

Individual pages: use generateMetadata for dynamic values. Detail pages read title, description, and cover image from the database:

// lib/generateDetailMetadata.js
export async function generateDetailMetadata(id) {
  const item = await fetchItemById(id);
  if (!item) return {};

  const slug = toSlug(item.displayName);
  const canonical = `${BASE_URL}/items/${id}${slug ? `/${slug}` : ""}`;
  const coverImage = item.imageUrl ?? null;

  return {
    title: item.displayName,
    description: item.description ?? "",
    alternates: { canonical },
    openGraph: {
      url: canonical,
      title: item.displayName,
      description: item.description ?? "",
      images: coverImage ? [{ url: coverImage }] : [],
    },
    twitter: {
      card: "summary_large_image",
      title: item.displayName,
      description: item.description ?? "",
      images: coverImage ? [coverImage] : [],
    },
  };
}

Use it in the page:

// app/items/[id]/[[...slug]]/page.js
export async function generateMetadata({ params }) {
  const { id } = await params;
  return generateDetailMetadata(id);
}

Static pages like the homepage can also export their own generateMetadata and set a canonical URL pointing to the root.

3. Semantic URLs: ID + slug#

Bare IDs (/items/abc123) are weak for SEO and readability. A common pattern:

/items/{id}/{slug}

The slug comes from the title and is human-friendly. The ID remains the primary key, so renaming only requires updating the slug.

When the slug is missing, redirect to the slugged URL to avoid duplicate content:

export default async function ItemPage({ params }) {
  const { id, slug } = await params;
  const item = await fetchItemById(id);
  if (!item) notFound();

  if (!slug) {
    redirect(`/items/${id}/${toSlug(item.displayName)}`);
  }

  return <ItemDetail item={item} />;
}

Every detail page’s alternates.canonical should point to the full URL including the slug.

4. Dynamic sitemap#

Next.js 13+ supports app/sitemap.js, which generates sitemap.xml at build or request time.

Combine static pages with dynamic database entries:

// app/sitemap.js
export default async function sitemap() {
  if (!isProd) return [];

  const staticUrls = [
    { url: BASE_URL, changeFrequency: "daily", priority: 1 },
    { url: `${BASE_URL}/about`, changeFrequency: "monthly", priority: 0.5 },
    { url: `${BASE_URL}/search`, changeFrequency: "daily", priority: 0.8 },
  ];

  const dynamicUrls = [];
  const items = await fetchAllPublicItems();

  for (const item of items) {
    const slug = toSlug(item.displayName);
    dynamicUrls.push({
      url: `${BASE_URL}/items/${item._id}${slug ? `/${slug}` : ""}`,
      lastModified: item.updatedAt ?? new Date(),
      changeFrequency: "weekly",
      priority: 0.7,
    });
  }

  return [...staticUrls, ...dynamicUrls];
}

Notes:

  • Only include public pages that should be indexed
  • Wrap per-collection fetches in try/catch so one failure does not break the entire sitemap
  • Return [] outside production

5. Structured data (JSON-LD)#

Meta tags tell crawlers the title and summary. JSON-LD tells them what kind of entity the page represents.

Map content types to Schema.org types:

// lib/generateJsonLd.js
export function generateJsonLd(item) {
  const url = `${BASE_URL}/items/${item._id}/${toSlug(item.displayName)}`;

  const base = {
    "@context": "https://schema.org",
    name: item.displayName,
    description: item.description,
    url,
    ...(item.image && { image: item.image }),
  };

  switch (item.type) {
    case "attraction":
      return { ...base, "@type": "TouristAttraction" };
    case "trip":
      return {
        ...base,
        "@type": "TouristTrip",
        startDate: item.startDate,
        endDate: item.endDate,
      };
    case "article":
      return {
        ...base,
        "@type": "Article",
        datePublished: item.createdAt,
        dateModified: item.updatedAt,
      };
    default:
      return null;
  }
}

Inject it in the page:

{
  jsonLd && (
    <script
      type="application/ld+json"
      dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }}
    />
  );
}

After launch, validate with Google’s Rich Results Test.

6. Control indexing by permission#

On UGC sites, not every user profile should reach Google. Apply business rules:

const isIndexable = item.permission === "public" && item.status === "approved";

return {
  title: item.displayName,
  description: item.description,
  alternates: { canonical },
  ...(!isIndexable && { robots: { index: false, follow: false } }),
};

For private, draft, or unapproved content: exclude from the sitemap and set noindex. That is easier than cleaning up URLs in GSC later.

7. Middleware: don’t let login walls block social crawlers#

With Auth0 or similar middleware, Facebook and Pinterest bots fetching OG previews may get blocked too.

Allow known crawler user agents through (they still get SSR; only auth checks are skipped):

// middleware.ts
const isSocialBot =
  userAgent.includes("facebookexternalhit") ||
  userAgent.includes("Pinterestbot");

if (isSocialBot) {
  return NextResponse.next();
}

Also exclude sitemap.xml and robots.txt from middleware:

export const config = {
  matcher: [
    "/((?!_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)",
  ],
};

Google Search Console Setup#

Once the code is in place, use GSC to prove site ownership and monitor indexing.

1. Add a property#

  1. Open Google Search Console
  2. Add a property using Domain or URL prefix
    • Domain: DNS verification; covers all subdomains and protocols
    • URL prefix: verifies a single prefix, e.g. https://www.example.com

2. Ownership verification (three common methods)#

DNS TXT (domain verification, recommended)

Add the TXT record Google provides to your DNS. One verification covers the whole domain.

HTML file

Place googleXXXX.html in public/ and visit https://www.example.com/googleXXXX.html after deploy.

HTML meta tag

// app/layout.js
export const metadata = {
  verification: {
    google: "your-verification-code",
  },
};

The Next.js Metadata API supports this natively—no manual <meta> tag needed.

3. Submit your sitemap#

After verification: Indexing → Sitemaps → Add https://www.example.com/sitemap.xml.

Within a few days, check discovered vs. indexed counts to confirm dynamic pages are being picked up.

4. What to monitor regularly#

  • Pages → Indexing: indexed, excluded, and error counts
  • Experience → Core Web Vitals: LCP, CLS, etc.
  • Links: external and internal link overview
  • URL Inspection: whether a single URL is indexable and which canonical Google chose

For new sites or large batches of new URLs, use URL Inspection → Request indexing to speed up initial discovery. You do not need to do this for every URL.

5. Other platforms (optional)#

  • Bing Webmaster Tools: can import GSC data
  • Pinterest and others: sometimes require a verification HTML file or meta tag in public/, similar to GSC

Post-mortem: a few things worth adding#

1. Draw the indexing boundary first#

Decide what should be searchable: public detail pages, listings, about page. What should not: settings, admin, editors, DMs.

Map that to robots.js, sitemap.js, and per-page robots meta so nothing slips through.

2. Canonical URLs are first-class#

Query strings, missing slugs, and legacy path redirects should all resolve to one canonical URL. Otherwise GSC will report “Duplicate, Google chose different canonical than user.”

3. Environment variables are your SEO switch#

Use NEXT_PUBLIC_BASE_URL to distinguish production from test. It is more reliable than NODE_ENV alone—some staging environments also run production builds.

4. A sitemap is a suggestion, not a guarantee#

Pages still need to be crawlable, have real content, not be noindexed, and load correctly. Meta tags, JSON-LD, and canonical URLs remain essential.

5. Test social previews separately#

Run URLs through the Facebook Sharing Debugger and Twitter Card Validator to confirm OG images and descriptions.

6. Performance is an SEO factor#

Core Web Vitals affect rankings. On the Next.js side: next/image, font optimization, and avoiding unnecessary large client bundles on detail pages.

7. Internationalization (if applicable)#

Use alternates.languages for hreflang tags to reduce duplicate-content issues across locales.

Minimal checklist#

Before launch, walk through this list:

  • Production root layout is not accidentally noindexed
  • Staging / preview environments are noindexed and disallowed in robots
  • robots.txt allows public pages and blocks private paths
  • sitemap.xml includes static pages and indexable dynamic pages
  • Detail pages have unique title, description, and canonical
  • OG + Twitter Card are configured with a default fallback image
  • Important content types have JSON-LD
  • URLs include slugs; missing slugs 301 to the slugged URL
  • Private content is noindexed and excluded from the sitemap
  • Middleware does not block sitemap, robots, or social crawlers
  • GSC is verified and the sitemap is submitted
  • Rich Results Test and social sharing debuggers pass

Closing thoughts#

The core idea of SEO in Next.js is simple: give crawlers the same clear, structured page information that users see, directly in server-rendered HTML.

The App Router’s metadata, generateMetadata, sitemap.js, and robots.js already standardize most of the plumbing. What actually separates good implementations is business logic: which pages to index, how to set canonicals, how dynamic data enters the sitemap, and how auth does not block crawlers.

Draw the boundary clearly, then ship against the checklist. That beats keyword stuffing every time.
