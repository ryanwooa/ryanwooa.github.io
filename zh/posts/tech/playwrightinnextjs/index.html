Jest 适合测函数和 API，但测不了「用户点按钮 → 跳转 → 地图加载 → 弹窗出现」这类完整链路。我们在 Next.js 项目里用 Playwright 搭了一套 E2E 体系：三桌面浏览器 + 两套移动端视口，并按 Desktop / Mobile 目录分层。这篇文章是复盘，不是官方文档翻译。

为什么选 Playwright#

对比 Cypress 等工具，Playwright 对我们这几个点特别合适：

  • 多浏览器原生支持：Chromium、Firefox、WebKit 一套 API
  • Mobile 模拟：内置 Pixel 5、iPhone 12 等设备 preset
  • Auth 状态复用：storageState 登录一次，全局复用
  • 与 Next.js 配合好：webServer 自动起 dev server；也可手动先 npm run dev 加速

项目里 Jest 继续负责单元/集成测试，Playwright 专门覆盖前端用户流程。

整体目录结构#

核心思路：按布局分层，按页面拆分，公共逻辑抽 helper。

tests/e2e/
├── auth.setup.js              # 登录一次，保存 cookie
├── authentication.spec.js     # 登录流程本身（单独 project）
├── helpers/
│   ├── pageHelpers.js         # 通用：跳过 tour、压 banner、等首页加载
│   ├── mapHelpers.js          # Desktop 地图交互
│   └── detailHelpers.js
├── desktop/
│   ├── homePage.spec.js
│   ├── detailsPage.spec.js
│   └── searchPage.js
└── mobile/
    ├── homePage.spec.js
    ├── mobileTabBar.spec.js
    └── objsPage2/
        └── objsPage2.map.spec.js

命名规则：**/*.spec.js，Desktop 和 Mobile 各跑各的，不混在一个文件里用 if (isMobile) 分支。

配置：用 Projects 实现多浏览器 + 分层#

playwright.config.ts 是整个体系的骨架：

import { defineConfig, devices } from "@playwright/test";
import dotenv from "dotenv";
dotenv.config();

export default defineConfig({
  testDir: "./tests",
  timeout: 90 * 1000,
  expect: { timeout: 45 * 1000 },
  fullyParallel: false,
  retries: process.env.CI ? 2 : 0,
  workers: 2,
  reporter: "html",

  use: {
    baseURL: "http://localhost:3000",
    actionTimeout: 15 * 1000,
    navigationTimeout: 30 * 1000,
    trace: "on-first-retry",
  },

  projects: [
    // 1. 先跑 setup，生成登录态
    {
      name: "setup",
      testMatch: /auth\.setup\.js/,
    },

    // 2. 登录流程单独测（不依赖 storageState）
    {
      name: "authentication",
      testMatch: /authentication\.spec\.js/,
      use: { ...devices["Desktop Chrome"] },
    },

    // 3. Desktop × 三浏览器
    {
      name: "chromium",
      testMatch: /desktop\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["Desktop Chrome"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },
    {
      name: "firefox",
      testMatch: /desktop\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["Desktop Firefox"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },
    {
      name: "webkit",
      testMatch: /desktop\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["Desktop Safari"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },

    // 4. Mobile × 两设备
    {
      name: "Mobile Chrome",
      testMatch: /mobile\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["Pixel 5"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },
    {
      name: "Mobile Safari",
      testMatch: /mobile\/.*\.spec\.(js|ts)/,
      use: {
        ...devices["iPhone 12"],
        storageState: "playwright/.auth/user.json",
      },
      dependencies: ["setup"],
    },
  ],

  webServer: {
    command: "npm run dev",
    url: "http://localhost:3000",
    reuseExistingServer: !process.env.CI,
    timeout: 180 * 1000,
  },
});

几个设计决策：

决策原因
testMatch 用路径区分 desktop/mobile不用在每个 test 里判断 viewport
dependencies: ["setup"]保证先登录再跑业务测试
fullyParallel: false有写操作、共享数据的用例避免并行冲突
reuseExistingServer: true（本地）已手动起 dev server 时跳过等待，快很多
全局 timeout 90sGoogle Maps、Auth0 跳转都偏慢

Auth0 登录：setup + storageState#

第三方登录每个 test 都走一遍 Auth0 太慢。用 setup project 登录一次，保存 cookie：

// tests/e2e/auth.setup.js
const { test: setup, expect } = require("@playwright/test");

const authFile = "playwright/.auth/user.json";

setup("authenticate", async ({ page }) => {
  await page.goto("/");
  await page.getByText("Sign In").click();

  await page.waitForURL(/.*auth0.com/);
  await page.locator('input[name="username"]').fill(process.env.AUTH0_USERNAME);
  await page.locator('input[name="password"]').fill(process.env.AUTH0_PASSWORD);
  await page.getByRole("button", { name: "Continue" }).click();

  await page.waitForURL(/localhost:3000/);
  await page.context().storageState({ path: authFile });
});

.env 里放测试账号：

AUTH0_USERNAME=test@example.com
AUTH0_PASSWORD=your_test_password

匿名测试时显式清空登录态：

test.describe("Unlogged", () => {
  test.use({
    storageState: { cookies: [], origins: [] },
  });
  // ...
});

登录流程本身单独放在 authentication.spec.js，走独立 project，与业务测试分开。

Desktop / Mobile：测什么、怎么分#

原则：共享组件只测一次，分叉 UI 分开测#

Mobile 和 Desktop 很多底层组件相同（比如 Card），但交互壳层不同：

  • Desktop 地图：marker 点击 → 浮层 overlay
  • Mobile 地图：marker 点击 → 底部 SlideUpPanel

Desktop 用 hover 触发的按钮，Mobile 必须直接可见、可 tap，不能依赖 .hover()。

Mobile 专用 locator#

Mobile 常有「DOM 里有两份、只显示一份」的情况，普通 getByTestId 可能匹配到隐藏节点：

const mobileHomeTab = (page, id) =>
  page.locator(`#${id}`).filter({ visible: true }).first();

const visibleSharePanel = (page) =>
  page.locator("#share-your-experience").locator("visible=true").first();

Helper 层：把稳定性逻辑集中管理#

测试文件应读起来像用户故事，等待、重试、跳过弹窗都放 helper。

通用 helper（pageHelpers.js）#

async function suppressBannerDialogs(page) {
  await page.addInitScript(() => {
    localStorage.setItem("locationPermission", "denied");
    localStorage.setItem("myapp_cookie_consent", "declined");
  });
}

要点：

  • 用 addInitScript 在页面加载前写 localStorage，比加载后再关 banner 稳
  • 用 isVisible() 而非硬等，tour 不出现时不报 timeout

跨浏览器导航重试（mapHelpers.js）#

Firefox / WebKit 在客户端路由竞态时容易抛 NS_BINDING_ABORTED，Chromium 往往没事：

export async function gotoStable(page, url, retries = 3) {
  for (let attempt = 0; ; attempt++) {
    try {
      await page.goto(url);
      return;
    } catch (err) {
      const isAbort =
        /NS_BINDING_ABORTED|interrupted by another navigation|frame was detached/i.test(
          err?.message ?? "",
        );
      if (!isAbort || attempt >= retries) throw err;
      await page.waitForLoadState("load").catch(() => {});
    }
  }
}

这类「只在某浏览器复现」的问题，值得写进 helper 并加注释，后人少踩坑。

按领域拆分 helper#

Helper职责
pageHelpers首页加载、跳过 tour、压 banner
mapHelpersDesktop 地图 marker、卡片菜单、filter
mobileMapHelpersMobile bottom sheet、tap 交互

测试文件怎么写#

1. 匿名 vs 登录分 describe#

test.describe("Unlogged", () => {
  test.use({ storageState: { cookies: [], origins: [] } });
  // 测公开页面、cookie banner、footer
});

test.describe("Logged In", () => {
  test.beforeEach(async ({ page }) => {
    await page.goto("/");
    await skipTourIfVisible(page);
  });
  // 测需要登录的功能
});

2. 有依赖的用例用 serial#

创建 → 编辑 → 删除这类流程：

test.describe("Logged In Map View", () => {
  test.describe.configure({ mode: "serial", timeout: 90000 });
  // Firefox 登录 + Google Maps 初始化慢，单独拉长 timeout
});

3. 优先用 role / testid，少用脆弱 CSS#

// 好
await page.getByRole("button", { name: "Delete" }).click();
await page.getByTestId("footer").toBeVisible();

// 地图等第三方组件不得不用 class
await page.locator(".gm-style").toBeVisible();

开发侧配合：关键交互点加 data-testid，E2E 会稳很多。

4. 数据不足时 skip，不要硬 fail#

test.skip((await link.count()) === 0, `Top Contents don't have ${type}`);

测试环境数据不稳定时，skip 比红一片更有用。

多浏览器踩坑复盘#

实际跑下来，三浏览器差异比预期大：

问题表现应对
Firefox 慢Maps 初始化 + 登录 setup 超 60s局部 timeout: 90000
WebKit 导航竞态page.goto 被客户端路由 abortgotoStable 重试
Google Maps marker点击时机因引擎而异dispatchEvent("click") + 重试循环
隐藏 DOM 节点Mobile 双份 markup，getByText 匹配多个.filter({ visible: true })
第三方 iframeMaps 在 iframe 里用外层 .gm-style 等稳定锚点

结论：不要假设 Chromium 过了就等于全过，CI 里至少跑 Firefox 或 WebKit 之一。

怎么跑#

# 全量（推荐本地先手动 npm run dev，更快）
npm run test:e2e

# UI 模式，调试神器
npm run test:e2e:ui

# 只跑 Desktop Chromium
npx playwright test --project=chromium

# 只跑 Mobile
npx playwright test --project="Mobile Chrome"

# 跑单个文件
npx playwright test tests/e2e/desktop/homePage.spec.js

# 看报告
npm run test:e2e:report

本地开发建议：先起 dev server，再跑测试。config 里 reuseExistingServer: true 会复用已有服务，比每次等 webServer 启动快不少。

结语#

Playwright 的价值不只是「能自动点按钮」，而是用项目结构把测试成本压住：

  • Projects 管浏览器和设备矩阵
  • 目录分层 管 Desktop / Mobile 差异
  • setup + storageState 管 Auth0 登录
  • helpers 管稳定性和跨浏览器补丁

从几个零散 spec 到 30+ 文件、覆盖首页/地图/详情/编辑/搜索，靠的不是多写断言，而是先把分层和复用设计对。如果你也在 Next.js + 第三方登录 + 响应式双布局的项目里，这套结构可以直接照搬。
