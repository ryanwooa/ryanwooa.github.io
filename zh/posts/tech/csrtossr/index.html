从前端数据库架构，逐步迁到 SSR

1. 我们原来的架构#

项目早期是一套「前端数据库 + 后端同步」的模式。

用户打开网站后，会先把数据从后端同步到浏览器里的本地数据库（IndexedDB / Dexie）。之后页面里几乎所有的读操作都走这层前端库，不再每次都打 API。

这套架构有一个很明确的优点：除了第一次加载慢，之后的体验非常快。列表翻页、详情切换、筛选排序，本质都是本地读，几乎没有网络延迟，有点像离线优先的 Web App。

但它有一个同样明确的短板：对 SEO 不友好。

爬虫和社交分享不会等你同步完本地库。它们拿到的是首屏 HTML 和初始 JS，看不到存在 IndexedDB 里的内容。详情页的 title、描述、正文，在搜索引擎和 Facebook 预览里要么是空的，要么是统一的壳页面。URL 也往往是 query 或统一路由，很难形成可索引、可分享的独立页面。

功能上跑得通，可见性上过不去。这是后来决定切 SSR 的根本原因。

2. 为什么不是推翻重来，而是逐步替换#

前端数据库架构已经撑起了大量页面和组件，一次性全改 SSR 风险太高：范围大、回归难、TTFB 可能全面恶化。

实际路径是渐进式迁移：

  • 先动页面层：详情、首页、Profile、About/Legal 等会被分享、被搜索的入口，改成 Server Component 在服务端拉主数据
  • 组件层暂时不动：很多子组件仍用 useEffect 拉次要数据，和原来习惯接近，改动面可控
  • 数据层同步演进：页面 SSR 要求服务端能直接查库或调 API，本地库从「唯一数据源」慢慢退成辅助或移除

不是「SSR 好、CSR 坏」的二选一，而是在不中断业务的前提下，把「必须被看见的内容」挪到服务端渲染。

3. 迁移时的分层思路#

页面：SSR 负责「必须首屏可见」的部分#

详情页的核心对象、首页的初始内容、Profile 的主文档、404 和权限判断——这些必须在 HTML 里就有。否则 SEO、分享预览、HTTP 语义（404 vs 200）都站不住。

同时借机改 URL：语义化路径、ID + slug、旧地址 redirect，和 SSR 一起做，避免以后还债。

组件：继续 useEffect，但要想清楚拉什么#

子组件不必为了 SSR 强行全改。评论、收藏、通知状态、侧边栏补充信息，很多本来就不是首屏关键路径，继续客户端拉数据合理。

要注意的是：页面 SSR 了，不代表组件可以无节制请求。原来读本地库几乎零成本，改成 API 后，每个 useEffect 都是真实网络开销。组件层迁移时要刻意控制——能合并的合并，能缓存的缓存（例如 SWR），避免「页面 SSR 快了、组件瀑布请求反而更慢」。

优化：SSR 不是免费午餐#

原来第一次慢、之后快；SSR 是每次请求都可能打服务端，TTFB 和 DB 压力都要重新评估。

我们实际在几件事上取舍：

  • 主数据 SSR，次要数据客户端补，不全塞一次服务端渲染
  • 能并行的查询并行，但控制并发，避免连接池被打满
  • 非首屏数据不阻塞首屏 HTML，让页面先出来，组件再填
  • 首页等公开页可配合 revalidate，减轻每次命中的成本
  • Guard、redirect 放 Server，减少客户端「先闪一下再跳转」

核心问题从「怎么让本地读更快」变成「服务端出哪些、客户端补哪些、各承担多少成本」。

4. 和前端数据库脱钩是配套的#

页面 SSR 后，Server Component 读不了 IndexedDB。原来「打开网站 → 同步到本地 → 页面读本地」这条链，对公开页和 SEO 页不再适用。

同期我们在做另一件事：读写逐步迁到 Backend API，本地库职责收缩。如果只改页面渲染、不改数据入口，会在 Server / Client 边界上反复打架——Server 拉一份、Client 又从本地库读一份，容易出现不一致。

渐进迁移的顺序大概是：公开页 SSR → 对应读路径改 API → 编辑/后台页稍后。不必等全站 API 化再动第一个 SSR 页面，但两条线要一起规划。

5. 踩坑复盘（结合旧架构）#

以为 SSR 能解决所有慢——以前慢在首次同步，SSR 后慢在服务端查询和 API 瀑布，问题换了地方，要重新量。

页面 SSR 了，组件还在狂拉 API——本地库时代无感的 N 次读，变成 N 次 HTTP，首屏体感可能更差。要有意识合并、缓存、懒加载。

SEO 页和编辑页混同一套数据路径——公开页必须走服务端可信数据源；编辑页可以继续 client-heavy，但要清楚边界。

slug、权限、404 仍放 Client 处理——本地库时代「没数据就空着」的习惯，SEO 场景下应改成 Server 端 notFound / redirect。

第一次加载 vs 每次加载的权衡——旧架构牺牲冷启动换热路径；SSR 改善可见性，但热路径可能多网络往返。要在产品层面接受这种 trade-off，而不是期待「又 SEO 又完全像本地库一样快」。

6. 和 SEO 工作的关系#

切 SSR 是 SEO 的前置，不是替代。Sitemap、robots、metadata、JSON-LD 可以后配，但若内容仍主要靠客户端 + 本地库呈现，这些配置作用有限。

我们的顺序是：先让会被搜到、会被分享的页面在服务端出内容和 meta，再补 sitemap、索引策略、Search Console。否则容易在空壳页面上做无用功。

7. 若你也在类似架构里，建议的优先级#

  1. 认清哪些页必须 SSR——详情、首页、公开 Profile，不是全站
  2. URL 和 SSR 一起改——一次到位，少积累 redirect
  3. 页面 SSR + 组件 useEffect 并存——合理，但要管控组件请求量
  4. 数据层跟页面迁移并行规划——API 化是 SSR 的配套，不是可选项
  5. 单独做性能预算——TTFB、API 次数、DB 并发，别用旧架构的体感预期衡量新架构

8. 结语#

我们的迁移不是从「纯 CSR」到「纯 SSR」，而是从**「前端数据库驱动的 SPA 体验」，转向「公开页服务端可见、交互页仍可客户端补数据」**的混合架构。

旧方案用首次同步换后续极速，在应用内体验上很划算，对 SEO 不划算。新方案用服务端首屏换可见性，代价是要重新设计数据路径和请求策略。

若你的项目也是本地库 + 同步起步，不必否定过去——那套在工具型、登录后产品里仍然有效。只是内容要被找到、被分享的页面，迟早要在 Server 上出内容。逐步替换页面、组件暂留 useEffect、同步优化 API 和请求，是比较稳的一条路。
